### 1.2 Google Motion Photo (MVIMG)

**格式定义**：

Google Motion Photo（MVIMG）采用单文件封装方案，将静态JPEG图像与短视频片段合并存储在同一个文件中。

**文件结构**：

```
┌─────────────────────────────────────────────────────────┐
│                    MVIMG 文件结构                        │
├─────────────────────────────────────────────────────────┤
│  JPEG 头部                                              │
│  ├── JPEG 图像数据                                      │
│  ├── EXIF 元数据                                        │
│  ├── XMP 元数据                                         │
│  │   └── MicroVideoOffset (视频偏移量)                  │
│  │   └── MicroVideoVersion (格式版本)                   │
│  └── JPEG EOI 标记 (0xFFD9)                             │
├─────────────────────────────────────────────────────────┤
│  视频数据 (MP4/H.264)                                   │
│  ├── 视频头部                                           │
│  ├── 视频帧数据                                         │
│  └── 视频尾部                                           │
└─────────────────────────────────────────────────────────┘
```

**关键XMP元数据字段**：

| 字段名 | 说明 | 示例值 |
|--------|------|--------|
| MicroVideoOffset | 从文件末尾向前偏移的视频字节数 | 1234567 |
| MicroVideoVersion | 格式版本号 | 1 |
| MicroVideoFPS | 视频帧率 | 30 |
| MicroVideoPreviewThumbnailWidth | 预览图宽度 | 1920 |
| MicroVideoPreviewThumbnailHeight | 预览图高度 | 1080 |

**技术特点**：

1. **单文件封装**：静态图与动态视频存储在同一文件，便于分享
2. **XMP指针定位**：通过MicroVideoOffset定位视频起始位置
3. **兼容性设计**：文件以JPEG开头，普通查看器可正常显示静态图
4. **反向解析**：从文件末尾向前偏移MicroVideoOffset字节即可提取视频

**实现工具**：

| 工具 | 功能 | 平台 |
|------|------|------|
| exiftool | 解析XMP元数据、提取视频 | 多平台 |
| mvimg (Python) | 分离/合并MVIMG文件 | Python |
| FFmpeg | 处理视频部分 | 多平台 |

### 1.3 Apple Live Photo

**格式定义**：

Apple Live Photo采用双文件配对方案，静态图像（HEIC/JPEG）与视频（MOV）分别存储，通过Content Identifier元数据关联。

**文件结构**：

```
Live Photo = HEIC文件 + MOV文件（通过Content Identifier配对）

┌───────────────────────────────────┐    ┌───────────────────────────────────┐
│           HEIC 文件               │    │           MOV 文件                │
│  ├── 静态图像数据                 │    │  ├── 视频帧数据 (H.264)           │
│  ├── EXIF 元数据                  │    │  ├── 音频数据                     │
│  ├── Content Identifier           │◄──►│  ├── Content Identifier           │
│  │   (UUID配对标识)               │    │  │   (相同UUID)                   │
│  └── 其他元数据                   │    │  └── QuickTime元数据              │
└───────────────────────────────────┘    └───────────────────────────────────┘
```

**关键元数据字段**：

| 文件 | 字段名 | 说明 |
|------|--------|------|
| HEIC | Content Identifier | UUID配对标识，与MOV文件相同 |
| HEIC | Content Identifier (Apple) | Apple特定标识字段 |
| MOV | Content Identifier | 与HEIC相同的UUID |
| MOV | Live Photo Key Frame Index | 关键帧索引 |

**技术特点**：

1. **双文件配对**：图像和视频分离存储，需保持配对关系
2. **Content Identifier**：通过UUID确保两个文件的关联
3. **iOS原生支持**：系统级集成，照片应用可无缝播放
4. **跨平台挑战**：非iOS平台需特殊处理才能保持"动态"特性

**配对保持机制**：

- 照片应用导入时自动识别配对关系
- iCloud同步时保持配对
- 分享到非iOS平台时通常转为静态图或视频

## 三、技术实现要点

### 3.1 水印添加时机

**核心难点**：

| 难点 | 说明 | 解决方案 |
|------|------|---------|
| 视频解码 | 需解码视频帧才能叠加水印 | FFmpeg解码 + 帧处理 |
| 帧同步 | 水印需同步叠加到所有帧 | 批量帧处理 |
| 性能开销 | 视频帧处理耗时较长 | 异步处理、GPU加速 |
| 格式重建 | 添加水印后需重建文件格式 | 保持文件结构完整性 |

**实现流程**：

```
动态照片文件
    ↓
解析文件结构（JPEG部分 + 视频部分）
    ↓
┌─────────────────────┬─────────────────────┐
│     JPEG部分        │     视频部分        │
│  ↓                  │  ↓                  │
│ 水印叠加            │ 视频解码            │
│  ↓                  │  ↓                  │
│ JPEG重新编码        │ 逐帧水印叠加        │
│                     │  ↓                  │
│                     │ 视频重新编码        │
└─────────────────────┴─────────────────────┘
    ↓
重新拼接（JPEG EOI + 视频数据）
    ↓
更新XMP元数据（MicroVideoOffset等）
    ↓
输出带水印的动态照片
```

### 3.2 水印位置策略

**兼容性挑战**：

| 挑战 | 说明 |
|------|------|
| 多格式差异 | 各厂商格式结构不同（单文件vs双文件） |
| 元数据差异 | XMP字段命名和结构各厂商不同 |
| 视频编码差异 | H.264参数可能不同 |
| 播放兼容性 | 水印处理可能影响原生播放器识别 |

**兼容策略**：

| 策略 | 说明 |
|------|------|
| 格式检测 | 通过元数据检测动态照片格式类型 |
| 结构保持 | 处理时保持原格式结构完整性 |
| 元数据更新 | 处理后更新相应元数据指针 |
| 回退机制 | 无法保持动态特性时转为静态图 |

### 3.3 EXIF保留问题

**EXIF处理难点**：

| 难点 | 说明 |
|------|------|
| 元数据完整性 | 水印处理需保留原始EXIF数据 |
| XMP同步 | XMP中的视频指针需同步更新 |
| 配对关系 | Live Photo的Content Identifier需保持 |
| 时间戳 | 处理时间可能影响元数据时间戳 |

**EXIF保留策略**：

```python
# EXIF保留处理流程示例
def process_motion_photo_with_watermark(input_file, watermark):
    # 1. 解析原始文件
    jpeg_data, video_data, exif_data = parse_motion_photo(input_file)
    
    # 2. 提取关键元数据
    micro_video_offset = exif_data.get('MicroVideoOffset')
    content_identifier = exif_data.get('ContentIdentifier')
    
    # 3. 处理JPEG部分（叠加水印）
    jpeg_with_watermark = add_watermark_to_jpeg(jpeg_data, watermark)
    
    # 4. 重建EXIF/XMP
    new_exif = rebuild_exif(exif_data, jpeg_with_watermark.length)
    
    # 5. 更新视频偏移指针
    new_micro_video_offset = calculate_new_offset(jpeg_with_watermark)
    new_exif['MicroVideoOffset'] = new_micro_video_offset
    
    # 6. 拼接输出
    output_file = concat(jpeg_with_watermark, video_data)
    
    # 7. 写入新元数据
    write_exif(output_file, new_exif)
    
    return output_file
```

## 六、小结

### 6.1 核心发现

1. **格式多样性**：各厂商动态照片格式存在差异，Google/Samsung/Huawei等采用单文件封装，Apple采用双文件配对。

2. **水印支持差异**：
   - Apple无原生水印功能，需第三方App
   - 大多数厂商水印仅叠加到静态帧（JPEG部分）
   - Xiaomi声称支持动态帧水印同步显示
   - Huawei支持图库后期编辑，但需转为静图

3. **技术实现难点**：
   - 视频帧水印叠加需解码所有帧，性能开销大
   - 格式兼容性需保持文件结构完整性
   - EXIF/XMP元数据需同步更新，特别是视频偏移指针

4. **跨平台兼容挑战**：
   - Live Photo配对关系需保持Content Identifier
   - MVIMG的MicroVideoOffset需更新
   - 不同厂商XMP字段命名不同

### 6.2 技术建议

1. **优先静态帧水印**：多数场景下仅处理静态帧（JPEG部分），避免复杂的视频帧处理。

2. **格式检测优先**：处理前检测格式类型，选择相应处理策略。

3. **降级机制**：无法保持动态特性时，提供转为静态图的降级方案。

4. **元数据完整性**：处理过程保持EXIF/XMP完整性，特别是视频偏移指针和配对标识。

5. **性能优化**：视频帧处理采用异步处理和GPU加速。

### 6.3 参考价值

动态照片水印方案为本文档所述产品提供以下参考：

1. **格式检测机制**：通过元数据检测动态照片类型
2. **分层处理策略**：静态帧优先、动态帧可选
3. **降级方案**：无法保持动态特性时的静态图方案
4. **元数据处理**：EXIF/XMP保留和更新机制
